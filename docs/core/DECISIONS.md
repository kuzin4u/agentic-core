# Журнал решений agentic-core

### К1. Отдельный пакет для общих механизмов
- **Решение:** механизмы, нужные двум и более проектам, живут в `agentic-core`; проекты подключают фиксированную версию.
- **Почему:** иначе журнал согласий, удержания и подпись были бы написаны в ПС-платформе, агенте, marketplace-api и НСВР по отдельности и разошлись бы.
- **Что меняет:** РП14 в ПС-платформе, Р16 в агенте, Н3 в НСВР, записи для marketplace-api.
- **Отменяет:** —

### К2. Нейтральные имена
- **Решение:** API пакета без предметных слов: `HoldLedger`, `HashChainJournal`, а не `MandateBudget`, `EscrowAccount`.
- **Почему:** один механизм удержаний обслуживает и бюджет мандата, и эскроу; предметная оболочка — у потребителя.

### К3. Тестовые векторы как контракт
- **Решение:** `vectors/vectors.json` — нормативная часть пакета; перенос на другой язык обязан их проходить.
- **Почему:** стек `buyer_agent` не зафиксирован; ядро должно оставаться единым по смыслу независимо от языка.

### К4. Подключение пакета
- **Решение:** до публикации в реестр пакетов — git-зависимость с тегом версии (`"@kuzin4u/agentic-core": "git+https://github.com/kuzin4u/agentic-core.git#v0.1.0"`).
- **Почему:** не нужен отдельный реестр; версия фиксируется тегом.

### К5. Протокольный слой ПАО — подмодуль `/pao`
- **Решение:** типы, клиент и сервер-заглушка ПАО v1.1 живут в отдельном подмодуле `@kuzin4u/agentic-core/pao`. Типы генерируются из копии `spec/agent-protocol.yaml` (источник — agentic-ps-platform@0bc924e, sha-256 `e6725aa4270155be5d0606cb366ca095fedc13a7d4e6c7b9500d25addf945ecb`); сгенерированный файл коммитится. YAML разбирает пакет `yaml`, подключённый только как devDependency генератора; во время выполнения внешних зависимостей по-прежнему нет. Предметные имена ПАО (`Mandate`, `MANDATE_*` и др.) допускаются только в `/pao`; основной вход пакета остаётся нейтральным.
- **Почему:** CO-3 по совместному плану ред. 3 — одна генерация типов на платформу (PS-02) и агента (AG-02), чтобы поля не могли разойтись. Переименование протокольных типов в нейтральные снова создало бы расхождение, ради устранения которого CO-3 и ставится. Копия спецификации в репозитории позволяет собирать и проверять пакет в CI без соседнего репозитория, а хэш показывает, от какой редакции ПАО сгенерированы типы.
- **Что меняет:** CLAUDE.md (таблица модулей, правило нейтральности, стек, раздел «Спецификация ПАО»), README (подключение `/pao`), ROADMAP (журнал изменений), STATUS. В PS-02 платформы и AG-02 агента типы ПАО импортируются из `@kuzin4u/agentic-core/pao`.
- **Отменяет:** — (уточняет К2 для подмодуля `/pao`, К2 остаётся в силе)

### К6. Хранилища PostgreSQL без драйвера в зависимостях (14.10.2026)
- **Решение:**
  1. **`SqlClient`.** Пакет принимает интерфейс `SqlClient { query(text: string, params?: unknown[]): Promise<{ rows: Row[] }> }`; `pg.Pool` и `pg.Client` подходят без обёртки. Драйвер выбирает и подключает потребитель; в `dependencies` пакета по-прежнему пусто, `pg` — только в devDependencies для тестов.
  2. **Одна SQL-команда на операцию.** Пакет не открывает транзакций: годится пул, где соседние запросы уходят на разные соединения.
  3. **Миграции файлами.** SQL-файлы поставляются в пакете (`sql/NNN_*.sql`) и применяются по порядку номеров средством потребителя. Для тестов и простых случаев — `applyMigrations(client)`: чтение через `node:fs`, учёт в таблице `core_migrations`.
  4. **`AsyncJournalStore` рядом с `JournalStore`.** Добавляются `AsyncJournalStore` (`last`, `append`, `all` возвращают `Promise`) и `AsyncHashChainJournal` с теми же `append`, `verify`, `extract`. `JournalStore`, `MemoryJournalStore`, `HashChainJournal` не меняются. Первая реализация — `PgJournalStore(client, chain)`.
  5. **Одна таблица на много цепочек.** Ключ `(chain, seq)`, `prev_hash` уникален в цепочке — развилка невозможна. Хэш хранится в строке; `chain` в хэш не входит, векторы журнала не меняются. `payload` — каноническая строка JSON (`text`), `at` — строкой, как пришло.
  6. **Только добавление — на стороне базы.** Строковый триггер `BEFORE UPDATE OR DELETE` и отдельный триггер уровня оператора `BEFORE TRUNCATE` (строкового TRUNCATE не бывает) отклоняют изменение. Обход триггеров суперпользователем находит `verify()` по хэшам строк.
  7. **Гонка добавлений.** Второе из одновременных `append` в одну цепочку получает нарушение ключа; журнал перечитывает конец цепочки и повторяет, число попыток ограничено, сверх него — ошибка вызывающему.
  8. **Цепочка привязана к своему имени** (дополнение 14.10.2026, ревью #19). У именованной цепочки `prev_hash` первой записи — `chainGenesis(chain) = sha256Hex("core_journal:" + chain)`, а не 64 нуля. Имя хешируется как UTF-8 **без нормализации Unicode**: одно видимое имя в разных нормальных формах даёт разные начала. Потребителям — ASCII-идентификаторы цепочек (`mandates:<client_id>`). `AsyncHashChainJournal` берёт начало у хранилища (`store.genesis`; у `PgJournalStore` — `chainGenesis(chain)`), `verify()` начинает с него: строки цепочки B под именем A не проходят на первой записи. Привязку проверяет `verify()`, а не `CHECK` в базе — суперпользователь обходит и то и другое. `entryHash` не меняется; безымянная цепочка (`HashChainJournal`, `MemoryJournalStore`) по-прежнему начинается с нулей. Вектор — раздел `journal_chain_genesis` в `vectors/vectors.json` (ASCII, кириллица, «й» в NFC и NFD с разными началами). Векторы `journal` не меняются; на PG они проверяются хранением — записи читаются побайтно те же.
  9. **Ограничение: удалённый хвост.** `verify()` находит изменённую запись, разрыв `seq`, перестановку и чужую цепочку под своим именем. Хвост, удалённый суперпользователем, и цепочку, пересчитанную целиком от начала, по одной таблице не обнаружить. Защита — внешний якорь: последние `seq` и `hash`, которые потребитель хранит отдельно или получает из подписанной выписки; хранение и подпись якоря — у потребителя, к PS-06 или SEC-2.
  *Дополнение пп. 10–13 (15.10.2026, CO-2; ревью #21):*
  10. **Удержания одной командой.** «Условное обновление с версией» — условие по остатку в том же `UPDATE` (`limit − committed − reserved ≥ amount`) под блокировкой строки счёта, вместе с изменением удержания — одним оператором (CTE с изменением данных). `version` увеличивается при каждом изменении счёта, но не сравнивается: чтение версии и затем `UPDATE … WHERE version = $v` — две команды, без транзакции счёт и удержание разошлись бы (п. 2). Повтор `ref` — нарушение `UNIQUE(ref)` откатывает оператор целиком, затем чтение прежнего удержания. Суммы — `bigint`; node-postgres отдаёт `bigint` строкой — на чтении проверка `Number.isSafeInteger`, иначе ошибка, а не тихая потеря точности. В базе — `CHECK` на инварианты остатка и `currency text NOT NULL`.
  11. **Идемпотентность — с состоянием «выполняется».** Ключ захватывается одной командой (`INSERT … ON CONFLICT`); одновременный вызов с тем же ключом, пока первый не завершён, получает `IdempotencyInProgress` (новый класс). Упавшая `fn` снимает захват. Захват — аренда сроком `leaseMs` (по умолчанию 60 с, не больше ttl результата; уточнение владельца 15.10, /audit № 8): если процесс упал во время `fn`, по истечении аренды ключ перезахватывается, а не висит «выполняется» до конца ttl (поправка 2 ревью 15.10). Запись результата — только владельцем захвата (метка захвата в строке): опоздавший после перезахвата результат не перезаписывает. `fn` дольше `leaseMs` может выполниться дважды — срок аренды выбирает потребитель по своей самой долгой операции. Истёкший по ttl результат — перезахват. Время — от переданных часов `now`; тест на поддельных часах. Ключи — в области `scope` потребителя.
  12. **Nonce — проверка и запись одной командой** (`INSERT … ON CONFLICT DO NOTHING RETURNING`), в области `scope`. Очистка — `purge()` без параметра границы: удаляются nonce старше `retainMs`, заданного в конструкторе; `retainMs` обязан быть ≥ 2 × окна времени проверки (`skewSec` у `verifyRequest`/`verifyRequestAsync`: обращение с меткой на краю окна принимается ещё `skewSec` после записи nonce), иначе — `RangeError` при создании хранилища, если окно передано, и требование в документации (поправка 3 ревью 15.10). Тест: повтор после `purge()` в пределах окна → отказ.
  13. **`verifyRequestAsync`** — как `verifyRequest`, но `seenNonce` асинхронный и вызывается последним, после проверки подписи: в базу пишутся nonce только подписанных обращений. Отличие кодов от `verifyRequest`: повтор nonce с отозванным ключом даёт `AGENT_KEY_REVOKED`, а не `SIGNATURE_INVALID`. `verifyRequest` не меняется.
- **Почему:**
  - Правило стека — без внешних зависимостей во время выполнения (расхождение №9). У потребителей уже свой пул и свои миграции; драйвер в пакете дал бы две версии `pg` и два пула.
  - Одна команда на операцию и интерфейс в один метод держат пакет независимым от драйвера.
  - Канонический JSON строкой, а не `jsonb`: `jsonb` хранит разобранное значение, а не запись — числа нормализуются, и совпадение пересчитанного хэша зависело бы от перевода чисел базой и драйвером; строку с `\u0000` `jsonb` не принимает вовсе. В строке хранится ровно то, что хэшировали.
  - Одна таблица на все цепочки — одна миграция у потребителя на все его журналы.
- **Что меняет:** CLAUDE.md («Стек», «Модули»); README (подключение пула и миграций — с кодом CO-1); `src/journal.ts`, `src/sql.ts`, `sql/001_journal.sql`, тесты; CI (сервис `postgres:16`); ROADMAP (журнал изменений); STATUS (№9); `vectors/` — новый раздел `journal_chain_genesis` (п. 8), прежние разделы не меняются. Версия — минорная, выпуск v0.3.0 после CO-2.
- **Отменяет:** —

### К7. ПАО 1.2.0 в пакете: таблица ошибок из спецификации, `retry` по РП16 (выпуск v0.2.1)
- **Решение:** копия `spec/agent-protocol.yaml` обновлена до ПАО 1.2.0 (agentic-ps-platform@04b7841, sha-256 `4f42e8b62599c88a8291ef3dd797c92e00a4932067eef23271c76943e4407940`). Генератор строит `PAO_ERRORS` из `x-pao-errors` (код → HTTP, `retry`, описание) и отказывает, если перечень не совпадает с `ErrorCode`. Ручной таблицы в заглушке больше нет. Заглушка отвечает по `PAO_ERRORS` и ставит `Retry-After` у 429 и 503. Клиент берёт `retry` из `PAO_ERRORS`, если пара «код, HTTP-статус» есть в таблице, иначе — из тела (код новее версии пакета). `same_key` — повтор с тем же `Idempotency-Key`, новыми nonce и подписью, ожидание не меньше `Retry-After`; `Retry-After` больше потолка или исчерпаны попытки — отказ вызывающему. `new_key` — отказ сразу: нужен новый ключ подписи. У запросов без тела — digest пустого тела (так и было с CO-3). Версия пакета 0.2.1 — совместимое изменение.
- **Почему:** РП16 платформы закрыл расхождения 2–4 пакета: смысл `retry` определён, digest пустого тела записан в §2, таблица ошибок перенесена в YAML.

### К8. Каталог продавца: каноническая модель, реестр форматов, свежесть (14.10.2026)
- **Решение:**
  1. **Каноническая модель.** Агент читает каталоги только в канонической модели.
     - Магазин: id, юрлицо (ИНН), MCC, способы оплаты, регионы доставки, условия возврата. Желательно: зона и знак готовности, рейтинг исполнения.
     - Товар: sku, штрихкод (GTIN/EAN), бренд, модель, ключевые атрибуты, название, категория, цена в копейках, валюта, наличие, срок и стоимость доставки, время обновления. Желательно: описание, фото.
     - Штрихкод, бренд, модель и атрибуты нужны, чтобы сопоставить один товар у разных продавцов.
     - Правило A5 — часть модели: цена и условия в полях совпадают с текстом и для агента те же, что для человека. Расхождение — признак нарушения, а не ошибка разбора.
  2. **Входные форматы продавцу не навязываются.** Коннектор переводит формат продавца в каноническую модель. Платформа платёжной системы каталоги не хранит и не агрегирует: это делает оператор агента или площадка.
  3. **Реестр реализации форматов** — `catalog/formats.json` в пакете, с тестом (CO-К2): формат, продавцы, оборот, дата оценки, статус (кандидат → в реализации → поддерживается). Формат включается в реализацию, когда суммарный оборот продавцов в этом формате превышает `catalog_format_turnover_threshold` = 10 млн ₽ в месяц (решение владельца 13.10.2026). Оборот — по продавцам воронки подключения с известными данными, не по оценкам рынка. Пересмотр — при каждом новом продавце в воронке и не реже раза в квартал.
  4. **Исключение из порога** — решением владельца: формат, нужный для стандарта или документа соответствия (фид ACP), включается без порога с пометкой «стратегический».
  5. **Свежесть — два режима.** Фид по расписанию — для поиска и сравнения, срок — `catalog_feed_max_age`. Живая проверка цены и наличия по sku перед каждым заказом обязательна; заказ по данным фида без проверки запрещён. Цену заказа по-прежнему считает продавец (инвариант 5).
  6. **Место в пакете** — подмодуль `@kuzin4u/agentic-core/catalog` по образцу К5; основной вход его не реэкспортирует.
- **Стартовый реестр:** YML (Яндекс.Маркет) — кандидат, первый к оценке; фиды Ozon, WB — кандидат; schema.org Product/Offer — кандидат; фид ACP — стратегический (решение владельца).
- **Почему:**
  - Требование нового формата — главный барьер подключения продавцов.
  - Порог по обороту ограничивает работу форматами, за которыми стоят деньги.
  - Живая проверка закрывает заказ по устаревшей цене.
  - Поля сопоставления нужны, чтобы агент сравнивал один и тот же товар.
- **Что меняет:** CLAUDE.md (модуль `catalog` — план; правило нейтральности — исключение для `/catalog`); ROADMAP (CO-К1, CO-К2, CO-К3 после 0.3; журнал изменений); STATUS. Код — в задачах CO-К1 (типы, валидатор, проверка A5; минорная версия), CO-К2 (реестр и порог), CO-К3 (коннектор YML, живая проверка). Потребители: агент — AG-К1…AG-К3; платформа — PS-К1 (сверка с её №17); набор продавца и площадки — UI-К3.
- **Отменяет / связано:** — Уточняет К2 для подмодуля `/catalog`, К2 в силе. **Соответствие номеров:** решение «К1» документа «2026-10-13 Каталог продавца и агент глазами клиента» (раздел 3) = К8 ядра; дополнение из решения «К3» того же документа (раздел 4, функция 2) — п. 1 (штрихкод, бренд, модель, атрибуты, срок и стоимость доставки). Остальные части «К3» — у агента, платформы и приложения, в ядро не входят.

### К9. Сумма — минимальные единицы и валюта; v0.3.0 ломающий (15.10.2026)
- **Решение:**
  1. **Тип суммы.** `Money = { amount: number; currency: CurrencyCode }`. `amount` — целое число минимальных единиц валюты, `Number.isSafeInteger(amount) && amount >= 0`; проверка — `assertMinor(n)`. Дробных сумм и `bigint` в API нет.
  2. **Код валюты.** `CurrencyCode` — строка, проверка `isCurrencyCode`: `^[A-Z][A-Z0-9]{2,11}$`. Подходят коды ISO 4217 (`RUB`, `JPY`, `KWD`) и зарегистрированные у потребителя коды активов (`USDC`); проверка не сводится к `[A-Z]{3}`. Перечня валют и таблицы знаков после запятой в ядре нет: ядро считает целые единицы и сравнивает коды; что такое «единица» у `JPY` (0 знаков), `KWD` (3) или `USDC` (6) — знает потребитель.
  3. **Одна валюта на операцию.** Сложение, сравнение и сплит — только в одной валюте; иначе `MoneyError("CURRENCY_MISMATCH")`. Пересчёта между валютами в ядре нет.
  4. **`money`.** Удаляются `assertKop` и `splitByWeights`. Добавляются `CurrencyCode`, `Money`, `MoneyError` (коды `BAD_AMOUNT`, `BAD_CURRENCY`, `CURRENCY_MISMATCH`, `BAD_WEIGHTS`), `assertMinor`, `isCurrencyCode`, `money(amount, currency)`, `addMoney`, `splitMoney(total: Money, weights: number[]): Money[]`. `addMoney` — сумма больше `MAX_SAFE_INTEGER` → `BAD_AMOUNT`, а не тихое переполнение (поправка ревью 15.10). Веса — неотрицательные безопасные целые (доли задаются целыми: базисные пункты, миллионные доли), сумма > 0; деление — через `BigInt`, без потери точности у границы `MAX_SAFE_INTEGER`; остаток — последней доле **с положительным весом** (`splitMoney(5 RUB, [1, 1, 0])` → `[2, 3, 0]`; поправка 1 ревью 15.10); валюта долей — валюта суммы.
  5. **`holds`.** Счёт открывается в одной валюте: `openAccount(id, limit: Money)`; у `Account` и `Hold` — поле `currency`. `reserve(account, amount: Money, ref, expires_at?)`, `commit(holdId, amount: Money, releaseRest?)`: другая валюта → `HoldError("CURRENCY_MISMATCH")`. `available(id)` возвращает `Money`. Повтор `reserve` с тем же `ref`, но другой суммой, валютой или счётом → `REF_CONFLICT`, как прежде.
  6. **Повторное открытие счёта** — тот же лимит и валюта → прежний счёт без изменений; иначе → новый код `HoldError("ACCOUNT_CONFLICT")`. Неверный код валюты на входе `holds` (`openAccount`, `reserve`, `commit`) → `HoldError("BAD_CURRENCY")`, как в `MoneyError`; неверная сумма — `BAD_AMOUNT` (уточнение владельца 15.10.2026, П2.1а). Так и в памяти, и на PG: прежняя тихая перезапись в `HoldLedger` теряла `reserved` — это ошибка, исправляется здесь.
  7. **Векторы.** Новый раздел `money`: `RUB`, `JPY`, код с 3 знаками (`KWD`), код актива вне ISO (`USDC`), сплит у `MAX_SAFE_INTEGER`, остаток при нулевом последнем весе, `addMoney` на границе `MAX_SAFE_INTEGER`, чужая валюта → `CURRENCY_MISMATCH`, плохой код → `BAD_CURRENCY`, `MAX_SAFE_INTEGER + 1` → `BAD_AMOUNT`. Раздел `holds` переписывается: суммы с валютой, плюс шаги «резерв в другой валюте», «повторное открытие тем же» и «другим лимитом». `version` векторов → 2. `canonical`, `journal`, `journal_chain_genesis` не меняются.
  8. **Версия — исключение для 0.x.** Правило «минор добавляет, мажор ломает» действует с 1.0.0. До 1.0.0 ломающее изменение допускается минорной версией по semver (0.y.z) — только через `/decision` и с разделом «Переход» в заметках к выпуску (в нём же — перевод дробных весов прежней `splitByWeights` в целые). v0.3.0 — ломающий: `money` и `holds`. Потребители фиксируют тег, поэтому переход — их задачей: платформа (на 0.2.1; `holds`, `money` пока не импортирует) и агент (AG-05, № 21 агента) переходят на 0.3.0 вместе.

### К12. `canonicalJson` отказывает на значениях вне JSON (№18); v0.5.0 (16.10.2026)
- **Решение:**
  1. **Отказ (`TypeError`)** — если в любом месте значения встретится:
     - `Date`, `Map`, `Set`, а также любой объект, прототип которого не `Object.prototype` и не `null`: экземпляры классов, `Buffer`, типизированные массивы, `RegExp`, обёртки `Number`/`String`/`Boolean`, `Error`. Массив (`Array.isArray`) допускается;
     - число `NaN`, `Infinity` или `-Infinity`. Сейчас здесь бросается `Error("NON_FINITE_NUMBER")`, после К12 — `TypeError` с тем же сообщением. Ловушки по `instanceof Error` продолжат работать.
  2. **Отказ (`TypeError`) и на прочих значениях вне JSON** — `undefined` как само значение или элемент массива, функция, `symbol`, `bigint`. Пункт сверх перечня №18 — вариант (а) владельца, 16.10.2026 (PR #24). Сейчас у них такое поведение:
     - `canonicalJson(undefined)` возвращает `undefined` при объявленном типе `string`;
     - `[undefined]` и `[() => 1]` дают `"[]"`, хотя `JSON.stringify` даёт `"[null]"`;
     - функция или `symbol` в поле объекта дают `{"f":undefined}` — это неверный JSON (проверено на `main`);
     - `bigint` уже бросает `TypeError` (из `JSON.stringify`).

     Дыра в массиве (`[, 1]`) — как элемент `undefined`; циклическая ссылка (объект или массив на своём же пути обхода) — `TypeError` `NON_JSON_VALUE`, а не `RangeError` переполнения стека; общая ссылка в разных ветвях циклом не считается (рекомендация из чата, 16.10.2026, PR #24).

     Поле объекта со значением `undefined` по-прежнему пропускается, как в `JSON.stringify`: это обычный способ записать необязательное поле.
  3. **Сообщения — коды, без текста для человека:**
     - `NON_FINITE_NUMBER` — для `NaN` и `±Infinity`;
     - `NON_PLAIN_OBJECT` — для п. 1;
     - `NON_JSON_VALUE` — для п. 2.

     Путь к значению в сообщение не попадает: в нём могли бы оказаться ключи из `payload` потребителя.
  4. **Векторы `canonical` не меняются**: все три входа — простые объекты, массивы и строки. Требование к переносам ядра на другие языки (К3) — тот же отказ на значениях вне JSON. Новый раздел векторов не нужен: отказ проверяется тестами ядра, а входов вроде `Date` в JSON векторов не бывает.
  5. **Версия v0.5.0** — минор, меняет поведение основного входа. Для 0.x это допускается по CLAUDE.md «Правила». В CHANGELOG будет раздел «Переход с 0.4.x»:
     - `canonicalJson`, а через неё `payload` журнала (`HashChainJournal`, `PgJournalStore`) и `body`/`result` идемпотентности (`IdempotencyStore`, `PgIdempotencyStore`) отказывают на значениях п. 1–2;
     - потребитель до передачи переводит дату в строку ISO 8601, `Map` — в простой объект, `Set` — в массив, экземпляр класса — в простой объект.
- **Почему:** `Date`, `Map` и экземпляры классов сейчас записываются как `{}` без ошибки. Данные молча пропадают: в журнале хэш считается от `{}`, а исходного значения нет, и проверка целостности его не вернёт; в идемпотентности повтор возвращает `{}` вместо результата. Пустой объект и потеря данных неотличимы, а отказ виден при первом же вызове. Платформа хэширует `payload` журнала согласий через `canonicalJson` в PS-06, поэтому решение нужно до PS-06. `Set` и `NaN` владелец добавил к перечню №18 16.10. Отказывать по прототипу, а не по перечню классов, надёжнее: перечень не закрыт, а прототип у простого объекта всегда `Object.prototype` или `null`, в том числе после `JSON.parse`.
- **Что меняет:** `src/canonical.ts`, тесты (каждый вид из п. 1–2, векторы прежние), README (раздел `canonicalJson`), CHANGELOG, `package.json` и `package-lock.json` (0.5.0), STATUS (№18 закрыт).

### К14. Коннектор YML: подмножество формата и свой разборщик XML без исполнения DTD (17.10.2026)
- **Решение:**
  1. **Подмножество YML.** `parseYml(input, profile, options)` в подмодуле `/catalog` читает из фида:
     - `yml_catalog@date` → `updatedAt` товаров. Нужен часовой пояс: если в дате его нет, берётся `options.offset` (например, `+03:00`); нет и его — ошибка `YML_DATE`;
     - `shop/currencies/currency@id`. `RUR` читается как `RUB`, курс (`rate`) не читается: цена берётся в валюте предложения;
     - `shop/categories/category` (`id`, `parentId`, текст) → `category` товара: путь от корня через « / »;
     - `shop/delivery-options/option` и `shop/pickup-options/option` (`cost`, `days`). `days`: «2» → 2…2, «1-3» → 1…3, «0» → в тот же день. Это варианты по умолчанию;
     - `offer` (`id`, `available`):
       - `name` → `title`; для `type="vendor.model"` — `typePrefix vendor model`;
       - `vendor` → `brand`, `model` → `model`;
       - первый `barcode` → `gtin`;
       - `price` и `currencyId` → `price`;
       - `categoryId` → `category`;
       - `description` → `description` (разметка в CDATA — как текст продавца, без очистки);
       - `picture` → `images`;
       - `param@name` (+ `@unit`) → `attributes` («вес»: «500 г»);
       - `count` → `availability.quantity`;
       - `delivery`/`pickup` = `false` убирает способ;
       - `delivery-options`/`pickup-options` предложения заменяют варианты магазина.

     Прочие элементы и атрибуты пропускаются без ошибки: неизвестные поля допускаются (К8 п. 1). `available="false"` → `inStock: false`; без атрибута — `true`.
  2. **Чего в YML нет, даёт потребитель** — профиль магазина `profile`:
     - `id`, `inn` (10 или 12 цифр), `mcc`, `paymentMethods`, `deliveryRegions`, `returns`;
     - по желанию `readiness`, `fulfillmentRating`.

     Коннектор только переносит их в `CatalogShop`, проверка — `validateShop`.
  3. **Цена — по К9.** Число из фида («250», «250.50», «250,50») переводится в минимальные единицы по `exponent` потребителя: таблицы знаков в ядре нет. Если знаков больше, чем `exponent`, — ошибка `YML_PRICE`, без округления. Отрицательное число, разряды через пробел и экспоненциальная запись — тоже `YML_PRICE`. Стоимость доставки читается так же.
  4. **Результат без исключений на данных продавца:** `{ shop, products, issues }`.
     - `issues` — `CatalogIssue { code, path }` с кодами `XML_*` и `YML_*`; путь — XPath-подобный, например `/yml_catalog/shop/offers/offer[2]/price`.
     - Предложение с ошибкой перевода в `products` не попадает. Ошибка XML — `products` пуст, `shop` — `null`.
     - Проверка модели (`validateShop`, `validateProduct`) и A5 (`checkProductA5`, `checkShopA5`) — отдельным вызовом потребителя: коннектор переводит формат, но не судит продавца (К8 п. 1: расхождение A5 — признак нарушения, а не ошибка разбора).
     - Исключение — только на ошибке вызова: неверный `exponent`, `offset` или пределы.
  5. **Разборщик XML — свой, внутренний** (`src/catalog/xml.ts`, из `/catalog` не экспортируется). Пакет остаётся без зависимостей во время выполнения. Подмножество:
     - объявление `<?xml … ?>`, элементы, атрибуты, текст, `CDATA`, комментарии; прочие инструкции обработки пропускаются;
     - сущности — только `&lt; &gt; &amp; &quot; &apos;` и числовые `&#…;`/`&#x…;` (допустимые символы XML). Другая сущность — `XML_ENTITY`, в том числе объявленная во внешнем DTD;
     - **DOCTYPE — строгий пропуск короткой формы** (решение владельца, чат, 17.10, PR #26):
       - пропускается только объявление без внутреннего подмножества (без `[`): `<!DOCTYPE имя>`, `<!DOCTYPE имя SYSTEM "…">`, `<!DOCTYPE имя PUBLIC "…" "…">` — например, шапка Яндекса `<!DOCTYPE yml_catalog SYSTEM "shops.dtd">`;
       - внешний DTD никогда не загружается и не читается;
       - длина объявления — не больше 1 КиБ; DOCTYPE допускается один раз и только до корневого элемента;
       - DOCTYPE с внутренним подмножеством, иной формы, повторный или после корня — `XML_DOCTYPE`;
     - кодировка: `Buffer` — по объявлению, UTF-8 или windows-1251 (через `TextDecoder` с `fatal`). Другая кодировка или неверная последовательность байт — `XML_ENCODING`. Строка принимается как уже декодированная;
     - пределы: `maxBytes` (по умолчанию 64 МиБ), глубина вложенности `maxDepth` (по умолчанию 64), атрибутов у элемента — не больше 256. Превышение — `XML_LIMIT`;
     - один проход без рекурсии и без регулярных выражений с возвратами: время линейно от длины входа. Проверяется тестом в worker (`tests/linear.ts`, как в CO-К1 П2.1а);
     - ошибка разбора — `XML_SYNTAX` со смещением в символах, без текста для человека.
  6. **Живая проверка цены и наличия** (К8 п. 5) — CO-К3 часть 2, отдельным пунктом К14 или своим решением, если понадобится порт к продавцу.
  7. **Версия** — v0.6.0 вместе с CO-К1, минор, только добавление. Основной вход и векторы не меняются: перевод формата — не механизм, который переносят на другой язык по К3.
- **Почему:**
  - Без зависимостей: в стеке ядра их нет во время выполнения. Готовые разборщики XML либо тянут зависимости, либо по умолчанию раскрывают сущности.

  - ИНН, MCC, оплаты и возврата в YML нет, а модель К8 их требует. Брать их из других полей фида (`company`, `url`) — домысел.

### К15. Живая проверка цены и наличия перед заказом: порт к продавцу, сравнение с каталогом, отказ при неясности (17.10.2026)
- **Решение:**
  1. **Порт.** В `/catalog` — интерфейс источника живого предложения:
     - `LiveOfferRequest { sku, quantity, region? }`: `quantity` — целое ≥ 1, `region` — код из `CatalogShop.deliveryRegions`;
     - `LiveOffer { sku, price: Money, availability: CatalogAvailability, checkedAt }`: `checkedAt` — время ответа у продавца, ISO 8601 с часовым поясом;
     - `LiveOfferSource { fetch(req, signal: AbortSignal): Promise<LiveOffer> }`.

     Транспорт (API продавца, ПАО, площадка) — у потребителя: в ядре нет сети и протокола конкретной платформы (правило совместимости 1).
  2. **Проверка.** `checkLiveOffer(product, req, source, options)` → `{ ok: true, offer }` или `{ ok: false, codes, offer }` (`offer` — `null`, если ответа нет или он не по форме). Функция не бросает исключений на поведении источника; исключение — только на ошибке вызова (неверные `req` или `options`). Сравнение без сети — синхронная `compareLiveOffer(product, offer, req, options)`, для ответа, полученного другим путём.
  3. **Коды без текста; каждый запрещает заказ:**
     - `LIVE_UNAVAILABLE` — источник бросил исключение, отклонил обещание или не ответил за `options.timeoutMs` (по умолчанию 5000 мс; по истечении — `abort()` сигнала);
     - `LIVE_INVALID` — ответ не по форме: `sku` не тот, `price` не `Money` по К9, `availability` не по модели, `checkedAt` не дата с поясом;
     - `LIVE_STALE` — `checkedAt` старше `options.maxAgeMs` (по умолчанию 60 000) или позже текущего времени больше чем на `options.clockSkewMs` (по умолчанию 30 000); часы — `options.now`;
     - `LIVE_CURRENCY` — валюта ответа не та, что в каталоге (курсов в ядре нет);
     - `LIVE_PRICE_UP`, `LIVE_PRICE_DOWN` — цена у продавца выше или ниже цены каталога;
     - `LIVE_OUT_OF_STOCK` — `availability.inStock` ложно;
     - `LIVE_QUANTITY` — продавец сообщил `quantity`, и оно меньше запрошенного.

     Кодов может быть несколько. При `LIVE_UNAVAILABLE`, `LIVE_INVALID` или `LIVE_STALE` сравнение не выполняется: данным ответа нельзя верить.
  4. **Допуск по цене — нет, строгое равенство** в минимальных единицах (решение владельца, вариант А, 17.10.2026, PR #27). Любое отличие — `LIVE_PRICE_UP` или `LIVE_PRICE_DOWN`, заказ не разрешён; потребитель обновляет позицию из `offer` и решает сам (например, спрашивает покупателя).
  5. **Отказ при неясности.** `ok: true` — только при полном совпадении: тот же `sku`, ответ свежий, та же валюта, та же цена, товар в наличии, количества хватает или оно не сообщено. Неожиданное исключение внутри проверки — `LIVE_UNAVAILABLE`, не разрешение. Повторов в ядре нет: один вызов источника на проверку, повтор решает потребитель.
  6. **Граница.** Проверка не считает цену заказа — её считает продавец (инвариант 5); она не даёт начать заказ по устаревшему фиду (К8 п. 5). `catalog_feed_max_age` (свежесть фида для поиска) в проверку не входит и остаётся у потребителя.
- **Почему:**
  - К8 п. 5 запрещает заказ по данным фида без живой проверки;
  - если её писать у каждого потребителя (агент, площадка), разойдутся правила свежести и коды;
  - порт отделяет механизм (ядро) от транспорта (потребитель);
  - ошибка в сторону разрешения стоит покупателю денег, в сторону отказа — одного повторного запроса;
  - по A5 (К8 п. 1) отличие цены — признак, что каталог устарел; допуск в ядре скрыл бы это расхождение.
- **Что меняет:** `src/catalog/live.ts`, `src/catalog/index.ts`; `tests/catalog-live.test.ts`; README («Живая проверка» в разделе `/catalog`); CLAUDE.md (строка `catalog`); ROADMAP (журнал, CO-К3); STATUS. Векторы и `spec/` не меняются. Версия — минор, только добавление, в v0.6.0. Потребители:
  - агент — AG-К1: реализовать `LiveOfferSource` к продавцу, звать `checkLiveOffer` перед каждым заказом, при `ok: false` заказ не начинать;
  - площадка (marketplace-api, план) — так же в агентском слое;
  - платформа — PS-К1: не затрагивается, каталоги она не хранит (К8 п. 2).
- **Отменяет:** — Дополняет К8 п. 5; закрывает К14 п. 6 (план живой проверки).

### К17. Формат записи реестра кодов отказов, подмодуль `/diag` (CO-ДГ; 18.10.2026)
- **Решение** (решение владельца от 18.10, PR #30; документ «2026-10-18 Система диагностики и коды отказов»):
  1. **Где лежит.** Формат — новый подмодуль `@kuzin4u/agentic-core/diag` (`src/diag/`): тип записи, перечни полей, проверка полноты. Основной вход его не реэкспортирует. Исключение из нейтральности имён — как `/pao` (К5) и `/catalog` (К8): в перечне источников есть «банк», «продавец», «клиент». Реестры конкретных кодов лежат рядом с кодами: ПАО — `/pao` (`PAO_DIAG`), каталог — `/catalog` (следующая сессия). Платформа и агент ведут свои реестры у себя в том же формате.
  2. **Запись** `DiagEntry`, все поля обязательны:
     - `code` — строка `^[A-Z][A-Z0-9_]*$`, машинное имя без текста;
     - `component` — `"core" | "pao" | "pi" | "platform" | "agent"`: кто выдаёт код — ядро, Платформа по ПАО, Платформа на порту участника (ПИ), Платформа вне протокола, агент;
     - `source` — непустой массив из `"agent" | "platform" | "bank" | "merchant" | "client" | "environment"`: кто ошибся или отказал; массив — потому что у `MANDATE_NOT_FOUND` источник неразличим (РП34);
     - `action` — `"stop" | "retry_same_key" | "after_fix" | "after_human" | "new_key"`: что делает получатель; те же пять значений, что `retry` ПАО (`never` ↔ `stop`, `same_key` ↔ `retry_same_key`).      - `since` — непустая строка: с какой версии действует (для `pao` — версия ПАО, для `core` — версия пакета, у агента и платформы — их версия или задача).

  3. **Проверка полноты** `checkDiagRegistry(codes, registry, { langs })` возвращает замечания кодами, без текста: `DIAG_MISSING`, `DIAG_EXTRA`, `DIAG_KEY_MISMATCH`, `DIAG_CODE_FORMAT`, `DIAG_ENUM`, `DIAG_EMPTY` (пустое поле или нет текста на языке из `langs`, по умолчанию `["ru"]`). Пустой массив — реестр полон. В каждом репозитории — тест `expect(checkDiagRegistry(...)).toEqual([])`: код без записи — красный.
  4. **Неизвестный код.** `diagAction(registry, code)` — `action` записи, для кода не из реестра — `"stop"` (при сомнении — отказ). Запись в журнал — у потребителя.
  5. **Реестр ПАО** `PAO_DIAG` (`/pao`) — 20 записей, по одной на код `ErrorCode` ПАО 1.4.0: `component: "pao"`; `since` — `"1.1.0"` у 18 кодов, `"1.3.0"` у `REQUEST_INVALID` и `KEY_INVALID` (К11); `action` из `PAO_ERRORS[code].retry` (тест сверяет); `source` — первая оценка документа владельца, для остальных кодов — оценка Claude Code в PR; тексты на русском. Модуль ручной, рядом с генерируемым `types.ts`; генератор и `x-pao-errors` не меняются. Если ПАО 1.5.0 перенесёт эти поля в `x-pao-errors`, ручной реестр заменит генерация (своим `/decision`).
  6. **Тексты.** Без персональных данных, путей с идентификаторами и бренда; без подстановок — постоянные строки, данные запроса в них не попадают. В ответах и журналах — только код, текст берётся из реестра в месте показа. Тексты для человека в ядре — исключение из правила планов 3 (В1, вариант А): по языкам, `ru` обязателен; показ и переключение языка — у потребителя.      - **Проверка** `SelfCheckItem`: `check` — машинное имя `^[a-z][a-z0-9_.]*$` (`db.migrations`, `keys.agent_expiry`, `pao.spec_hash`), без повторов в отчёте; `status` — `"ok" | "warn" | "fail"`; `code` — код из реестра, обязателен при `warn` и `fail`, запрещён при `ok`. Свободного текста, значений ключей, путей с идентификаторами и персональных данных в отчёте нет: тексты для человека и оператора — из реестра по `code` в месте показа (п. 6).

Вход функция не проверяет — для этого `checkSelfCheckReport`.
     - **Проверка отчёта** `checkSelfCheckReport(report, registry)` — замечания `{ code, check?, field? }` без текста, пустой массив = корректно: `SELFCHECK_EMPTY` (`checks` пуст или не массив), `SELFCHECK_FIELD` (`component` вне перечня, `version` пуста, `checked_at` не ISO 8601 UTC, `ready` не `boolean`, `status` вне перечня), `SELFCHECK_CHECK_FORMAT` (`check` не по шаблону), `SELFCHECK_DUPLICATE` (`check` повторяется), `SELFCHECK_CODE_MISSING` (`warn`/`fail` без кода), `SELFCHECK_CODE_FORBIDDEN` (код при `ok`), `SELFCHECK_CODE_UNKNOWN` (кода нет в `registry`), `SELFCHECK_READY_MISMATCH` (`ready` ≠ «нет `fail`»). `checked_at` проверяется только по формату: шаблон `YYYY-MM-DDTHH:MM:SS[.sss]Z` (миллисекунды необязательны) и `Date.parse` не `NaN`; строгая календарная проверка — v0.10.0 (строгий разбор дат; уточнено К18 п. 6, 19.10.2026; *было:* «v0.9.0»). Какие реестры передать — решает потребитель: свой или объединённый со ядерным (`{ ...PLATFORM_DIAG, ...PAO_DIAG }`); совпадение `component` записи реестра с `component` отчёта не проверяется.
     - **При `ready: false`** — поведение у потребителя, норма формата: компонент не принимает рабочий трафик (fail-closed), пишет отчёт в журнал одной строкой JSON и завершает запуск с ненулевым кодом. Отдача отчёта по сети — ПАО 1.5.0 (метод возможностей), не сейчас.
     - **Коды самопроверки** ведёт каждый компонент в своём реестре (`component: "platform"` / `"agent"`, обычно `action: "after_fix"`); ядро своих кодов самопроверки не добавляет.
     *Было:* «Отчёт самопроверки (следующая сессия). Общий формат отчёта самопроверки при старте — в `/diag`: „готов / не готов“ и список проверок с кодами из реестра, чтобы платформа (PS-ДГ) и агент (AG-ДГ) не придумывали его по-своему».

Порядок жёсткий — сначала формат в ядре, затем PS-ДГ и AG-ДГ. ### К18. Клиент ПАО: перенаправлениям не следует, подписант необязателен, реестр кодов клиента; v0.9.0 (19.10.2026)
- **Решение** (решение владельца, чат, 19.10.2026, окно А, PR #34; передача #32 от агента, AG-ДГ):
  1. **Перенаправления.** `PaoClient` передаёт в `fetch` параметр `redirect: "manual"` для всех операций ПАО, подписанных и неподписанных. Отказом считается:
     - любой ответ со статусом 300–399;
     - ответ с `type === "opaqueredirect"` (так `manual` выглядит в браузере, статус там 0);
     - ответ с `redirected === true` — на случай, если `fetch` потребителя не учёл параметр и уже прошёл по перенаправлению.
     Отказ — `PaoCallError` с кодом клиента `PAO_CLIENT_REDIRECT`, без повтора. `inspectResponse` при этом не вызывается, тело ответа не разбирается, по `Location` клиент не обращается. Так подпись, заголовки агента и тело не уходят на чужой хост, а конфигурацию ПАО нельзя подменить через `/.well-known` (#32 п. 1). Принцип тот же, что у РП40 платформы для push.
  2. **Реестр кодов клиента** `PAO_CLIENT_DIAG` лежит в `/pao` (`src/pao/client-diag.ts`), рядом с клиентом, в формате К17. Записи: `component: "core"`, `since: "0.9.0"`, `norm: "К18; #32"`, тексты на русском. Перечень кодов `PAO_CLIENT_CODES` и тип `PaoClientCode` экспортируются. Тест: `checkDiagRegistry(PAO_CLIENT_CODES, PAO_CLIENT_DIAG)` → `[]`. Коды:
     - `PAO_CLIENT_REDIRECT` — `source: ["agent", "platform", "environment"]`: неверный адрес Платформы у агента, перенаправление у Платформы или посредник; `action: "after_fix"` — частая причина в неверном адресе, а клиент перенаправлению не следует, поэтому утечки нет. Текст для оператора: проверить адрес Платформы; если адрес верный — возможна подмена ответа, оформить инцидент;
     - `PAO_CLIENT_SIGNER_MISSING` — `source: ["agent"]`, `action: "after_fix"` (п. 4).
     `PAO_DIAG` не меняется: в нём ровно 20 кодов `ErrorCode` ПАО 1.4.0 со сверкой со спецификацией.
  3. **Код в ошибке.** У `PaoCallError` появляется новое поле `clientCode?: PaoClientCode`; для таких отказов `message` равен этому коду. Геттер `code` по-прежнему возвращает только `ErrorCode` ПАО: его тип не расширяется, и `switch` потребителя по кодам ПАО не ломается. У отказа клиента `body` нет, `retry` — `never`. Действие для получателя — из `PAO_CLIENT_DIAG` через `diagAction`.
  4. **Подписант необязателен.** В `PaoClientOptions` поле `signer?: Signer`.
     - Если клиент собран без подписанта, `call` по типам принимает только неподписанные операции — `PaoUnsignedOperationKey` (сейчас `GET /.well-known/pao-configuration`). Вызов подписанной операции не компилируется.
     - Перечень строит генератор (`scripts/gen-pao.mjs`) из спецификации: операции без параметра `Signature`. Ручного списка нет; `spec/` не меняется.
     - Для кода на JS и приведения типов есть проверка во время выполнения: подписанная операция без подписанта даёт `PaoCallError` (`status: 0`, `attempts: 0`, `clientCode: "PAO_CLIENT_SIGNER_MISSING"`) до запроса в сеть.
     - Клиент с подписантом и клиент, собранный из переменной типа `PaoClientOptions`, принимают все операции, как в v0.8.0.
     - `agentCode` остаётся обязательным.
  5. **Что не меняется.** Состав подписи, повторы по `retry` (К7), заголовки неподписанного запроса (CO-1, v0.8.0), `PaoStub`, `PAO_DIAG`, основной вход, `vectors/`, `sql/`, `spec/`. `dependencies` пусты.
  6. **Версия — v0.9.0, минор, а не патч v0.8.1.**
     - Выпуск добавляет экспорты (`PAO_CLIENT_DIAG`, `PAO_CLIENT_CODES`, `PaoClientCode`, `PaoUnsignedOperationKey`, поле `clientCode`) и делает поле `signer` необязательным. По CLAUDE.md «минор добавляет».
     - Отказ на 3xx — в CHANGELOG в разделе «Изменено», без «Перехода»: в `x-pao-errors` и `errors` операций ПАО 1.4.0 ответов 3xx нет, `PaoStub` их не даёт.

### К19. Матрица испытаний и эмулятор ситуаций, подмодуль `/trials`; v0.10.0 (19.10.2026)
- **Решение** (решение владельца, чат, 19.10.2026, окно А, Р-74 реестра развилок чата; текст — PR #35, #issuecomment-6274106845, «да» с уточнениями — #issuecomment-6274212417; ревью чата — #issuecomment-6274133160):
  0. **Обозначения.**
     - **РЗ-N** — развилка N реестра развилок чата: РЗ-N = Р-N реестра. Не путать с решениями агента (Р26, Р37…), платформы (РП-N) и ядра (К-N).
     - **КП-N** — конфликт N пула: КП-N = К-N в `docs/reference/pul/29-konflikty.html` платформы, К1…К20. Не путать с решениями ядра К-N.
     - В копии списка развилок `id` остаётся как у чата (`Р-74`). Ссылку `РЗ-74` строит загрузчик.
  1. **Формат ситуации** `TrialSituation` — только данные, без функций (ситуацию можно хранить в JSON и перенести на другой язык, как векторы):
     - `id` — уникален в каталоге;
     - `refs` — непустой список `РЗ-N` / `КП-N`, которые ситуация покрывает;
     - `params` — `{ имя: [значения JSON…] }`, у каждого параметра список не пуст;
     - `exclude?` — недопустимые сочетания: список частичных наборов `{ имя: значение }`;
     - `expect` — ожидаемый исход по принятому решению: правила `{ when?: { имя: [значения] }, outcome }`, берётся первое подходящее. Сочетание без подходящего правила — ошибка каталога, не пропуск;
     - `outcome` — объект JSON (`TrialOutcome`). Совпадение — по подмножеству: каждый ключ ожидаемого есть в фактическом и равен ему по `canonicalJson`; прочие ключи фактического не сравниваются;
     - `rejected` — отклонённые варианты решения: `[{ variant, note, must?: "any" | "all" }]`, `variant` — имя, которое понимает стенд, `note` — какой вариант реестра. Пустой список — только вместе с `rejectedNone: { basis, reason }` (основания п. 5).
  2. **Движок и порт стенда.**
     - Порт `TrialStand` у потребителя: `run({ situation, refs, params, variant }) → Promise<TrialOutcome | TRIAL_UNSUPPORTED>`, `variant` — `"chosen"` или имя отклонённого варианта. Ядро не знает платформу и агента. Чистое состояние на каждый случай — забота стенда.
     - `runTrials(stand, situations, options) → Promise<TrialReport>`: случаи последовательно, предел времени на случай `timeoutMs` (по умолчанию 10 000). Отчёт: число случаев, `passed`, `failures` — `{ code, situation, refs, key, params, variant, expected, actual?, error? }`.
     - Коды прогона: `TRIALS_MISMATCH`, `TRIALS_UNSUPPORTED`, `TRIALS_STAND_ERROR`, `TRIALS_TIMEOUT`, `TRIALS_REJECTED_PASSED`, `TRIALS_REJECTED_UNSUPPORTED`. `formatTrialFailure` — одна техническая строка (код, ссылки, ключ, параметры); текстов для человека нет.
     - Ядро не зависит от vitest: потребитель проверяет `report.failures` или строит `it.each` из `expandCases`.
  3. **Сетка, выборка, воспроизведение.**
     - Ключи параметров упорядочены по кодовым точкам (как в `canonicalJson`), значения — в порядке объявления; номер сочетания — смешанная система счисления по этому порядку. Ключ случая — `<id>#<номер>`, от зерна не зависит.
     - `mode: "grid"` — полный перебор без `exclude`; больше `maxCases` (по умолчанию 1000) — `TRIALS_GRID_TOO_LARGE`.
     - `mode: "sample", n, seed` — `n` разных номеров сетки, mulberry32 от `seed` (целое без знака, 32 бита), без возврата; `n` не меньше размера сетки — полный перебор. Зерно обязательно и попадает в отчёт; `Math.random` нет.
     - `replayCase(stand, situation, key, variant?)` — повтор по ключу без зерна; `params` можно передать явно (если ситуация изменилась).
     - Смена генератора или нумерации меняет случаи при том же зерне — ломающее, только через `/decision`.
  4. **«Отклонённый вариант обязан провалиться»** (`rejected: true`, по умолчанию): каждый `rejected[i].variant` прогоняется на тех же случаях; при `must: "any"` (по умолчанию) хотя бы на одном случае исход не совпадает с ожидаемым по решению, при `"all"` — ни на одном. Иначе `TRIALS_REJECTED_PASSED` (испытание не различает решения); стенд не умеет вариант — `TRIALS_REJECTED_UNSUPPORTED`. Оба — провал, не пропуск.
  5. **Полнота.**
     - `checkCoverage({ items, situations, exclusions }) → TrialProblem[]`, `items` — область репозитория `trialScope(repo)`. Каждый пункт покрыт ситуацией или стоит в `exclusions` — «вне испытаний» `{ ref, basis, reason, recordedIn }`; `basis` из `TRIAL_EXCLUSION_BASES`: `legal` (юридическое), `pilot` (проверяется на пилоте), `external` (внешнее согласование), `process` (процесс, не код); `reason` не пуст.
     - Коды: `TRIALS_UNCOVERED`, `TRIALS_UNKNOWN_REF`, `TRIALS_EXCLUSION_BASIS`, `TRIALS_EXCLUSION_REASON`, `TRIALS_COVERED_AND_EXCLUDED`. Ситуация может покрывать и пункт чужой области (сквозные агента, КП-12 и КП-13 со стороны агента — ревью чата п. 1); обязательна своя.
     - Каждый пункт реестра назначен ровно одному репозиторию из `TRIAL_REPOS` (`agentic-core`, `agentic-ps-platform`, `agentic-buyer-ref`, `nsvr-settlement`, `marketplace-api`); тест ядра проверяет назначение. Полнота зелёная в каждом репозитории — значит покрыто всё.
