# agentic-core — общие механизмы агентной коммерции

## Что это

Библиотека, на которую опираются все проекты агентной коммерции и расчётов. В ней живут механизмы, которые иначе были бы написаны трижды: в Платформе платёжной системы, в ядре агента покупателя, в агентном слое маркетплейса и в расчётном контуре НСВР.

**Правило без дублирования:** если механизм нужен двум проектам, он живёт здесь. Проект не копирует код ядра, а подключает пакет фиксированной версии.

## Модули

| Модуль | Что делает | Кто использует |
|---|---|---|
| `canonical` | Каноническая сериализация JSON, sha-256 | все |
| `journal` | Журнал только на добавление с хэш-цепочкой, проверка целостности, выписка | ПС-платформа (журнал согласий), НСВР (история сделки), marketplace-api (ст. 15), агент (журнал решений) |
| `holds` | Удержания: резерв → закрепление → освобождение, частичное закрепление, истечение, идемпотентность по ref | ПС-платформа (бюджет мандата), НСВР (эскроу через BankAdapter) |
| `idempotency` | Повтор с тем же ключом → прежний результат, другое тело → конфликт | все API |
| `signing` | Подпись и проверка HTTP-обращений: состав полей, digest, окно времени, nonce, статус ключа; интерфейс Signer для ГОСТ | ПС-платформа, агент, marketplace-api, НСВР |
| `events` | Исходящая очередь с повтором и входящий дедупликатор | ПС-платформа, НСВР, агент |
| `money` | Сумма в минимальных единицах с валютой (К9), распределение без потери единицы | marketplace-api (сплит), НСВР (раскрытие с долями) |
| `catalog` (подмодуль `/catalog`, план — CO-К1, К8) | Каноническая модель каталога продавца, проверка A5, реестр форматов `catalog/formats.json`, живая проверка цены и наличия | агент (AG-К1), ПС-платформа (PS-К1), набор продавца |
| `pao` (подмодуль `/pao`) | Типы ПАО v1.3, генерируемые из `spec/agent-protocol.yaml`, и таблица ошибок `PAO_ERRORS` из `x-pao-errors`; клиент с подписью и повторами по `retry`; сервер-заглушка для контрактных тестов | ПС-платформа (PS-02), агент (AG-02) |

Хранилища в пакете — в памяти и на PostgreSQL (К6, v0.3.0): асинхронные интерфейсы рядом с синхронными (`AsyncJournalStore` рядом с `JournalStore`, `AsyncHoldLedger` рядом с `HoldLedger`, `AsyncIdempotencyStore` рядом с `IdempotencyStore`, `verifyRequestAsync` рядом с `verifyRequest`); `PgJournalStore`, `PgHoldLedger`, `PgIdempotencyStore`, `PgNonceStore`; драйвер передаёт потребитель через `SqlClient`, SQL-миграции — файлами в `sql/` (001–004).

## Тестовые векторы

`vectors/vectors.json` — эталонные входы и выходы: каноническая сериализация, хэши журнала, начала именованных цепочек (`journal_chain_genesis`, К6 п. 8), суммы (`money`, К9), сценарий удержаний с валютой, слабые ключи Ed25519 (`ed25519_weak_keys`, К10). Любой перенос ядра на другой язык (например, если `buyer_agent` на Python) обязан проходить те же векторы. Векторы меняются только через `/decision`, затем `npm run vectors`.

## Спецификация ПАО

`spec/agent-protocol.yaml` — копия из agentic-ps-platform с хэшем и коммитом-источником в `spec/SOURCE.md` (К5). Меняется только через `/decision`, затем `npm run gen:pao`.

## Правила

- Пакет не знает о предметной области: нет слов «мандат», «сделка», «эскроу» в API — только счёт, удержание, запись, событие. Предметные названия — у потребителей. Исключение — подмодуль `/pao` (К5): в нём имена протокола ПАО как есть; основной вход их не реэкспортирует. Так же — подмодуль `/catalog` (К8): модель каталога продавца.
- Обратная совместимость: минорная версия добавляет, мажорная ломает; потребители фиксируют версию. До 1.0.0 ломающее изменение допускается минорной версией — только через `/decision` и с разделом «Переход» в заметках к выпуску (К9 п. 8; v0.3.0).
- Правки — после «да» владельца. Коммит — с подтверждения владельца. Push в ветки `task/*` и PR Claude Code делает сам; слияние PR и теги — только владелец. Push в `main`, принудительный push, push тегов блокирует хук `guard.py`.
- Сумма — целое число минимальных единиц (`Number.isSafeInteger`, ≥ 0) и код валюты: ISO 4217 или код актива потребителя (К9). Номеров карт и персональных данных в пакете нет и быть не может.

## Работа через GitHub (с 12.10.2026)

Ревьюер из чата claude.ai читает репозиторий через коннектор GitHub и пишет
только комментарии в PR. Слияние и теги — только владелец, в терминале.

### Начало задачи
1. Ветка task/<код> от свежего main (git checkout main && git pull).
2. Сразу push ветки и черновой PR (gh pr create --draft): в описании — план
   задачи (нормы, инварианты, файлы, проверки, время) и раздел «Кирпичи»
   (см. ниже).
3. Владелец просит ревьюера «проверяй <репо> #N»; дальше ждать «да» или
   «читай ревью».

### Кирпичи (Д2, 14.10.2026)
- Задача делится на кирпичи с кодами К<N>.<M> (К1.1, К1.2…); подшаг —
  буквой (К1.1а). Кирпич — одна проверяемая правка.
- В agentic-core кирпичи — П<N>.<M> (П1.1, подшаг П1.1а), К<N> — решения
  DECISIONS (решение владельца 15.10.2026).
- В описании PR — раздел «Кирпичи»: таблица «Кирпич | Коммит | Состояние».
  Пустой коммит «план: …» для чернового PR — без подтверждения.
- Кирпич = отдельный коммит, только после «да» владельца; в сообщении
  коммита — код кирпича первым словом.
- После каждого кирпича — отметка в таблице через gh pr edit N --body-file …
  (хэш коммита, что проверено).
- Новый шаг из ревью — новой строкой с источником («ревью из чата № 3»);
  перенесённый — строкой со ссылкой на STATUS «Открыто» и задачу.

### Решения
- Текст /decision до записи — комментарием в PR (gh pr comment N --body-file …),
  в окне — только вопрос владельцу. Запись в DECISIONS — после «да».

### «Читай ревью #N»
- Комментарии ревьюера начинаются с «Ревью из чата:» — все комментарии в PR
  от аккаунта kuzin4u, автор различается только по этой метке; свои ответы
  начинай с «Claude Code:».
- gh pr view N --comments; разобрать замечания ревьюера: блокеры — исправить,
  остальное — исправить или в STATUS «Открыто» с адресом задачи; ответ —
  комментарием в PR (что сделано, что перенесено и куда).

### Чек-лист
- Перед коммитом: git status -sb — ветка task/*, не main; файлы явно, без
  git add -A, если не оговорено.
- Перед «готово к слиянию»: CI зелёный; /finish закоммичен в эту же ветку;
  PR переведён из черновика (gh pr ready N).
- Слияние, тег, «PR слит» — не делать и не утверждать: только после того, как
  владелец сообщит вывод `✓ Merged` и `git log --oneline -1` на main.
- Тег — только на коммит слияния main, только владелец.

## Совместимость с планами «Россия» и «Запад»

Правила обоих планов ред. 4 (`docs/reference/joint-plan.md` — «Россия», общее
ядро; `docs/reference/plan-west.md` — «Запад»); проверяются на ревью каждого
кирпича.

1. **Только через порт.** Ядро даёт механизмы; протокол конкретной платформы
   (ПАО, Visa, Mastercard, НСПК) — только в своём подмодуле (как `/pao`) или у
   потребителя, основной вход его не реэкспортирует.
2. **Сумма — число в минимальных единицах + валюта** (ISO 4217 или код актива).
   В ядре — с v0.3.0 (К9): `Money` в `money` и `holds`; таблицы знаков после
   запятой в ядре нет.
3. **Экраны — с переключением языка и настройкой бренда.** Экранов в ядре нет:
   ядро не содержит текстов для человека и бренда, только коды.

## Стек

TypeScript, Node ≥ 20.19 (`engines`, П3 служебной 14.10), без внешних зависимостей во время выполнения (только `node:crypto`, `node:http`, `node:fs`); генератор типов ПАО использует devDependency `yaml`. PostgreSQL (К6): пакет принимает `SqlClient { query(text, params) }`, драйвер — у потребителя; `pg` — только devDependency для тестов. vitest.

`/start`, `/finish`, `/task`, `/audit`, `/verify`, `/decision`.
